# Production Code Review — 2026-06-12

Full-stack review of Poker Tracker Pro (React/Vite client + Express/Prisma/PostgreSQL server)
focused on **correctness, data integrity, security, and production readiness**. This review
supplements the earlier feature-oriented audit in `docs/ai-audit/`.

The triaged action list lives in [BACKLOG.md](./BACKLOG.md). Changes are tracked in
[WORKLOG.md](./WORKLOG.md).

---

## Method

- Read all server services, controllers, middleware, utils, schema, and app wiring.
- Traced the two money-critical flows end to end: (1) completed-session create → settlement,
  (2) live session start → rebuy → add player → end → settlement.
- Verified suspected issues with `grep`/usage checks rather than assuming.
- Confirmed there are **zero automated tests** in the repository.

---

## Findings

Severity: **P0** = correctness/data-integrity/money bug or release blocker · **P1** =
security/robustness · **P2** = product gap / enhancement.

### P0 — Correctness & data integrity

**F-01 · `validateSettlements` is a no-op (broken + dead code).**
`server/src/services/settlementService.ts:68-77` computes `totalIn` and `totalOut` from the
*same* expression (`s.amount`), so it can never detect an imbalance — it always returns `true`.
It is also never called anywhere. Either implement it correctly (sum per-payer vs per-payee, or
validate against the source balances) or remove it. A "validator" that always passes is worse
than none because it implies a guarantee that does not exist.

**F-02 · No server-side validation in the live-session flow.**
`liveSessionService.addRebuy`, `addPlayer`, and `endSession` accept `amount` / `buyIn` /
`cashOut` straight from the request body with no type or range checks (confirmed: the file
imports none of the validators). A negative, `NaN`, `undefined`, or absurdly large value is
written directly to the database, corrupting `buyIn`/`cashOut` and downstream stats and
settlements. The completed-session path (`sessionService`) validates these; the live path does
not.

**F-03 · `endSession` is not transactional.**
`liveSessionService.endSession` updates every entry's `cashOut` via `Promise.all` of independent
`update` calls, then separately flips the session to `COMPLETED`. If any update rejects, the
session is left half-written (some cash-outs saved, status still `IN_PROGRESS`, no settlements).
The only `$transaction` in the codebase is in `addRebuy`. Wrap the end flow in a transaction.

**F-04 · Zero-sum mismatch surfaces as an opaque 500.**
`calculateSessionSettlements` throws a generic `Error('Session is not zero-sum…')`. The error
handler only special-cases messages containing "not found", so this becomes a 500 "Internal
Server Error". In practice chip counts at a real table rarely reconcile to the cent, so this is a
*routine* end-of-night condition, not an exceptional one. It should be a clear 400 with the
discrepancy amount surfaced to the user (this is almost certainly why the "Force End" escape
hatch was added — it papers over the real problem).

**F-10 · `calculateSettlements` mutates its caller's input.** (Found by TDD, not by reading.)
The function clones the *debtors* array but builds `creditors` with `.filter().map(b => ({...b}))`
— wait, the original only cloned debtors: `creditors` was `.filter().sort()`, holding references
to the caller's balance objects. The greedy loop then does `creditor.balance -= amount`, zeroing
the caller's creditor balances as a side effect. `calculateSessionSettlements` happens to use a
throwaway local, limiting today's blast radius, but it is a latent landmine (and broke the
post-condition validator added for F-01). Fixed by cloning both sides.

**F-05 · No test coverage on money logic.** The settlement greedy algorithm, ROI/win-rate/streak
calculations, and rebuy math are pure functions with zero tests. These are flagged HIGH RISK in
the existing `production-risk-audit.md` yet have no safety net. This is the single biggest
production-readiness gap.

### P1 — Security & robustness

**F-06 · Role-based access is enforced client-side only.**
`client/src/context/RoleContext.tsx` stores the role in `localStorage` and gates UI on `canEdit`.
The server performs **no** authorization — every mutating endpoint is open. A VIEWER (or anyone
with the URL) can mutate data with a direct API call. Acceptable *only* if the app is treated as
fully trusted/single-tenant; must be documented as a known limitation, and is a hard blocker for
any multi-user/auth story (existing IMP-011).

**F-07 · CORS is misconfigured.** `app.ts:19-23` sets `origin: '*'` together with
`credentials: true`. That combination is invalid per the CORS spec (browsers reject credentialed
wildcard) and is over-permissive. Set an explicit allow-list from `CORS_ORIGIN`.

**F-08 · No rate limiting / no `helmet`.** The API has no rate limiter (existing IMP-009) and
sets only a handful of headers by hand. Add `express-rate-limit` and `helmet`.

**F-09 · `reopenSession` 24h window keys off `updatedAt`.** Any later update mutates `updatedAt`,
so the reopen window is computed from the wrong timestamp. Minor, but the guard is unreliable.

### P2 — Product gaps (carried from prior audit, still open)

- Player notes exist in schema but have no UI (IMP-003).
- Profit-by-location / profit-by-day analytics (IMP-001/002).
- Undo/edit a rebuy in a live session (IMP-008).
- Photo upload UI for `photoUrls` (schema-only today).
- No CI to actually enforce "don't merge if red" (IMP-015).

---

## What is NOT broken (verified)

- Soft-delete (`deletedAt: null`) filtering is applied consistently across stats, summary, and
  session queries.
- The settlement greedy loop terminates correctly (each iteration zeroes at least one side
  exactly, so no infinite loop) and is zero-sum by construction.
- Prisma uses a singleton client (connection-pool fix already in git history).
- Streak math handles the break-even-breaks-streak rule as documented.

---

## Recommended sequence

1. Stand up a test harness (Vitest) — prerequisite for "don't commit unless green".
2. Lock the money logic under unit tests (F-05), which also pins F-01.
3. Fix F-01 → F-04 with tests proving each.
4. Harden security: F-07, F-08, then F-06 decision.
5. Add Playwright E2E for the two money-critical user flows against a disposable test DB.
6. Add CI to enforce green.
7. Then resume the P2 feature backlog.
